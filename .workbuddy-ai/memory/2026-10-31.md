## 02:05 原版头衔的 capital 对齐 EU5 首都（31 个）

用户："很多从EU5头衔转换为原版头衔的头衔，缺乏首都，或者首都不在EU5首都，统统修了"。

**范围**：`gen_debug/eu5_ck3_title_map.csv` 里 kind=country、`ck3_key` 是**原生** d/k/e/h 键（不含 `_eu5_`）的行 —— 共 93 个。其中 61 个本来就对，31 个要改（30 个值错 + 1 个缺 capital），1 个跳过。

**映射口径**：EU5 `countries[tag]["capital"]` 是 **location 名**（`venice`/`milano`/`palma`），不是 county。CK3 侧 `b_<location>` 的父 `c_` 就是该首都所在的伯爵领，`capital` 一律写成 `c_`（原版三个文件里 2482 个 capital 全是 `c_`，没有 `b_` 写法）。

**新脚本** `gen_debug/_fix_title_capital.py`（幂等，`--dry-run`）：
- 有 `capital` 行 → 就地改值；没有 → 在 `X = {` 后按 `key 缩进+1` 插入一行；
- 三道门：目标键未声明 / EU5 首都无对应 `b_` / **目标县在 title_map 里的 owner 不是该国** → 跳过并打印原因。

**改动 31 个**：
- `00_landed_titles.txt` 26：ARA→c_barcelona、BRI→c_vannetais、CAS→c_valladolid、CHA→c_vijaya、CHI→c_shuntian、COC→c_mayapan、CRS→c_orkhon、ETH→c_argobba、HUN→c_buda、JMB→c_lower_jambi、KBO→c_kanem、LOR→c_pays_nancy、MCM→c_desmond、MOR→c_fez、NOR→c_akershus、PEG→c_martaban、SCO→c_fife、SER→c_kosovo、TEU→c_upper_prussia、TFL→c_tafilalt、TIB→c_lhato、TLE→c_tlemcen、TUN→c_tunis、VLR→c_vladimir、VTN→c_vientiane、YEM→c_zabid
- `zz_eu5_titular.txt` 2：DLH→c_central_doab、GLH 插入 c_beljamen
- `zz_vanilla_titulars.txt` 3：GEN→c_levante、PIS→c_pisa、VEN→c_venice（原来都是 `c_gen_buamu_4`，那个 key 根本不存在）

**唯一跳过**：MEN `k_mentese`，EU5 首都 `milas` 在 CK3 里**没有 `b_milas`**，唯一落点是 `c_aydin`，而该县归 AYD。MEN 是 0 县国家，靠附庸 TVS 持 `c_mugla`，`c_mugla` 才是它实际首府 → 保持不动。

**唯一跨法理**：KBO `e_kanem_bornu` 的 capital 改成 `c_kanem`，但 `c_kanem` 在 CU 树里挂在 `e_maghreb > k_sahara > d_kanem` 下，不在 `e_kanem_bornu > k_kanem` 里（k_kanem 的县是 c_kawar/c_bornu/c_bagirmi/c_bomokandi）。其余 30 个新首府都确认落在自己头衔的 de jure 范围内。

**解析坑（写诊断脚本必踩）**：landed_titles 里 `color = { 249 232 247 }` 这种**单行块**会被 `^(\w+)\s*=\s*\{` 当成新键压栈，导致后续 `capital` 挂到 `color` 上。正则必须写成 `^([A-Za-z0-9_]+)\s*=\s*\{\s*(#.*)?$`（要求行尾就是 `{`，允许行尾注释——`e_hindustan` 就带 `# Titular, ...`）。另外同一 key 若在多文件声明，游戏按文件名排序后加载覆盖，取**最后一个**而不是第一个。

**风险提示**：`00_landed_titles.txt` 是 Crusader Universalis 的产物，重跑 CU 更新/Ck3MapGen 会覆盖这 26 个 capital。`zz_vanilla_titulars.txt` 里 1315 个未绑定的 landless titular 仍然共用 `capital = c_gen_buamu_4`（不存在的 key），本次只改绑定的 3 个。

**校验**：`--dry-run` 幂等 0；三个文件括号平衡 0、裸 LF 0、BOM 保留；93 个目标复查剩 1（MEN，预期）。

## 14:45 宗族对齐规则 v2（rurikovich 漏配追因）

用户："EU5罗德里克这么明显的怎么没有改成CK的留里克" → "为什么没匹配到，规则是不是有问题" → "我不希望你只是补单项，我重视的是更新规则" → "加上按照文化匹配，继续"。

**追因（旧规则三个盲区）**：
1. 候选集 = `dynasty_merge_map.json` 的 42 个归并父宗族；`rurikovich` 是**独立 dynasty**（mod 里只出现 1 次、无任何 house 引用），从不进归并 map → 整项被漏。mod 实际 1111 个 dynasty 块，归并只覆盖 210 个。
2. 匹配靠 `name` 字段，但 name 是本地化键且错译：`rurikovich` 的 name = `name_roderick`（罗德里克），vanilla 正确是 `dynn_Rurikid`（留里克）；"罗德里克"在 vanilla 是另一个键 `dynn_Rotreik`。拿 name 匹配必然漏。
3. culture 未归一化：dynasty 里 culture 还是 EU5 key（`muscovite`），CK3 没有 muscovite 文化（对应 `russian`），硬比 culture 会漏。另发现 `_apply_eu_culture_dynasty.py` 的映射键带 `_culture` 后缀，而 dynasty 里写不带后缀的 `muscovite`，所以那个脚本对 dynasty 的 culture 根本没生效。

**规则 v2**（脚本 `gen_debug/_align_dynasty_v2.py`，文档 `gen_debug/dynasty_alignment_rule.md`）：
- 候选集 = 全部 `*_dynasty`；匹配键 = KEY 去 `_dynasty`；culture 经 `_culture_classification.csv` target 归一化；名字评分 = difflib ratio + 受控词根加分（前缀≥5 且长度差≤4 才提升，避免短名假满分）。
- 分层 A(精确+文化)/B(高相似+文化)/C(中相似+文化，误配多)/D(名字强但文化不符或无 culture)/E/N。

**结果**（`gen_debug/dynasty_alignment_candidates.csv`）：A=112 B=58 C=145 D=221 E=453 N=94（custom 1083）。
- rurikovich 诊断：`core=rurikovich, norm_culture=russian -> 705 dynn_Rurikid, score=0.850`（B 层，规则本可捕获）。
- 已知误配（C 层，证明不能自动）：hanau→Hainaut、hohnstein→Holstein、tamura→Tomura、chiavelli→Crivelli、neville→Mandeville。
- D 层跨文化同名可疑：bali→bedouindyn014 dynn_Bali（巴厘岛 vs 贝都因）。

**已落地单项**：`rurikovich` 的 name 已改 `dynn_Rurikid`，alias 文件追加 `rurikovich_dynasty = 705`（ce_rurikid.dds）。
